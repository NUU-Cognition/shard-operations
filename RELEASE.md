# 0.8.0

The Tasks shard merges into Operations, and the shard gets the projects note (the fleet storage-1112, the operator request of 2026-11-12). One shard now does each task verb: it makes the task note in the Flint and the task in Ops, linked both ways.

- **The task workflows, skills, knowledge, and scripts move from the Tasks shard 0.6.0.** The workflows `create_task`, `scope_task`, `do_task`, `create_and_do_task`, `review_task`, and `do_task_group` (each with its invocation file, `flint shard invoke ops <workflow>`). The skills `capture_as_task`, `use_task`, `place_task`, `split_task`, `merge_tasks`, `continue_task`, `chain_tasks`, `group_tasks`, and `close_task`. The knowledge `knw-ops-task_model`, `knw-ops-task_cli`, and `knw-ops-task_commits` (the former `knw-task-model`, `knw-task-cli`, and `knw-task-commits`). The scripts `flint shard ops task-new|task-link|task-sync`, with their shared code `note-lib` and `task-lib`. The text and the step ids do not change, except the names.
- **The init** gets § Tasks: the Task Note and the Ops Task (the two parts, the hard rule of the task object, task or subtask, placement, the status and the review request, WIP commits, the task scripts, and the task invocations), the task workflows and skills in § Workflows and Skills, the job rows for a task, and the phases and the interaction model of the task workflows in `# Headless`. The duty of an agent session at a task stays in § Agent Sessions at Ops Objects.
- **Create task makes both parts.** `sk-ops-create_task` makes the task with `flint shard ops task-new <place>` (a task note and an Ops task), reads the place from `ops route` when the request names none, and checks `task.homeLabel` of `ops task show`. `sk-ops-use_operations` gives `task-new` for the job "Create a task". A planning write of many tasks (a deliverable setup, a plan, an inbox triage) can still make Ops tasks alone with `ops task create`; each such task gets its note when its work starts (`task-new --ops <ref>`).
- **`task-new` and `task-link` take each place of `ops task create`:** `--section`, `--project`, `--deliverable`, `--deployment`, `--parent`, `--master`, and `--unplaced`. The former `--subsection` works as `--section`. Two places are a refusal before any write. `sk-ops-place_task` uses `ops task home --section` (the former `--subsection` is hidden in the CLI).
- **The projects note.** The new script `flint shard ops projects-note [--org <org>] [--dry-run]` writes `Mesh/(System) Ops Projects.md`: the projects of the Ops org whose Flint place (of the project or of a deliverable) is this Flint, the project with the name of this Flint, the likely projects of `ops route`, and a table of all projects, each with its address, its web link, its open deliverables, and its deployments. It reads only from Ops. It keeps the `id` of the note and the text under `# Notes`. The init (§ The Projects of This Flint) tells an agent to read the note at the start, and to refresh it when it is older than 7 days.
- **The setup.** The manifest declares `setup: flint`. The setup file `setup-ops.md` runs `projects-note`, then `flint shard setup ops --complete`. An install or an update to 0.8.0 sets the setup to `required`, so `flint shard start ops` refuses until the setup is complete.
- **The dependency.** Operations depends on the Projects shard `^1.6`: a task note uses its type `Task` and its template `tmp-proj-task-v0.2`.
- **The migration** `mig-ops-0.7.0-to-0.8.0` (an agent step) checks the dependency, rewrites the commands and links of the Tasks shard in the instruction files of the Flint, keeps the Tasks shard installed, and does the setup.
- **Images and videos in Updates** (the media of lane OPS, Repos/main 3433bbdee1; the final text is `apps/cli-ops/docs/media.md`). `knw-ops-cli` § media: `ops media attach <task> <path...> [--body <text>|-] [--body-file <path>] [--no-comment] [--no-ffmpeg]` (one Update with an embed `![[ops-media:<fileId>]]` on each line), `ops media list|url|get|detach`, the limits (an image at most 20 MB, a video at most 100 MB), ffmpeg (faststart and a poster; with no ffmpeg, one notice), the output, the signed URLs, the connector, the exit codes, and the error codes. `knw-ops-data_model` § Media in Updates: the embed, the table `media_files`, the lifecycle (`pending`, `live`, `detached`), the limits and the quotas, the access, the ops `media.begin|confirm|readUrls|list|detach`, and the upload. The init (a job row, item 5 of the duty, the CLI summary, and a rule), `sk-ops-use_operations` (a job row, recipe 17, Safety Rule 9, and four troubleshooting rows), and Stage 3 of `do_task` and of `create_and_do_task` (a screenshot or a recording of a visual result) give it. The media ops reach a deployment at its next deploy; before it, `ops media` gives `agent_unknown_operation` or `media_storage_unconfigured`.
- The Tasks shard 0.6.1 is deprecated: its init points to Operations. It stays published.

# 0.7.0

Agent sessions at Ops objects (Task 448 of the NUU Operations Flint, the fleet total-orchestration-1111, D5, D15, D17, D19, D27, W13, and W19 of its contract). The new verbs come from the lane OPS of the fleet. The ops `agentSessions.defaults` and `agentSessions.setDefaults` reach a deployment at its next deploy. Before it, the defaults verbs give `agent_unknown_operation` ("not deployed yet").

- **The duty of an agent session at an Ops object.** A person can start an agent session at a task, a section, a deliverable, or a project, or attach a session that runs. The session keeps the object as an item, works for the person who attached it, answers a person first, reads each change when `orbh:objects` says that the object changed, does the changes of a review and requests the review again, and posts progress as short comments. The init (§ Agent Sessions at Ops Objects, model item 13, the job table, and the headless rule 11), `sk-ops-use_operations` (the model, the job "See the agents", recipe 16, a safety rule, and three troubleshooting rows), and `knw-ops-data_model` (§ Agent Sessions at Ops Objects) give it.
- **Two equal ways to speak to an agent.** A comment on a task (`ops comment add <task> "<text>"`) or a message in the chat of the session (`flint orbh chat send "<text>"`, `flint orbh chat read`; the Page shows the unread chat first, in the block `CHAT`). Only a task carries comments: at a section, a deliverable, or a project, a person speaks in the chat. The session answers in the place where the person wrote, before its other work.
- **A comment of a person is a message to the agent session** (the dev check of the fleet). Orbh gives the content of an object as data, and that rule stays for each other content: the duty gives a comment its force. The session answers each comment of a person with a comment (`ops comment add`), also when it asks for something, never in the chat. It does what a comment asks when it is a part of the work on the object. When it is not sure, it asks in a comment, and does not do it. The init, `sk-ops-use_operations` (the model and recipe 16), and `knw-ops-data_model` say it.
- **`ops agents`.** `ops agents [list] [--computer <name>] [--all]` lists the agent sessions at Ops objects now, with the read `live:objects` of NUU Network (the read of the page Agents). One verdict line, then one line for each session, the working sessions first. In the personal workspace it sends no org. A refused sign-in is `network_sign_in` (exit 3). `knw-ops-cli` § agents gives the true `--help` of each verb.
- **The agent defaults.** `ops agents defaults <ref>` shows the agent defaults of a task, a section, a deliverable, or a project, each value with its source. `ops agents defaults set <project or deliverable> [--flint] [--flint-id] [--computer] [--site] [--profile] [--mode]` sets them, and `none` clears a value. `knw-ops-data_model` § Agent Defaults gives the fields (`flintAddress` and `flintId`, and `agentDefaults` of a project and a deliverable), the order of the read, the two ops, and the codes `agent_defaults_invalid` and `agent_session_not_found`.
- The rule of `wkfl-strk-ops_do` ("no other comment") does not stop an answer to a comment of a person.
- The production `ops` has no `ops mode` (Task jn7emraj of the NUU Operations Flint, commit 5bb3795 of another session).

# 0.6.0

The features of NUU Operations up to ops-overnight-1109 (2026-11-09). The new commands come from the lanes CLI-T (Trident) and CLI-W (the work model) of the fleet; the new gateway ops come from the lane GW. Each new command reaches prod at the release of the fleet. Before it, a command on prod data gives `agent_unknown_operation` ("not deployed yet").

- **Trident** (streams and workspaces). `knw-ops-data_model` § Trident: a stream is a lane of work with a state (`active`, `paused`, `done`), attachments (projects, deliverables, sections), a size, and drawings. A stream step is a row of `plan_nodes` with a `streamId`. Its zone comes from its state (planned, active, done), and the shore is a part of the planned zone. Parked steps, substreams, cross links (they gate nothing), the move to another stream, the undo scope `stream:<id>`, the workspaces, every op of `streams.*` and `tridentWorkspaces.*`, the limits, and the codes. `knw-ops-cli` § stream and § workspace give `ops stream …`, `ops stream step …`, `ops stream substream …`, `ops stream drawing …`, and `ops workspace …`. `ops step` gets `split`, `split-beside`, `state`, `done-next`, `move-links`, `remove-links`, and `place` (`plans.splitNode`, `splitBeside`, `setStepState`, `doneAndNext`, `moveLinks`, `removeLinks`, `setBoardPositions`), and each `ops step` verb takes `--stream <stream>`.
- **Shares.** `knw-ops-data_model` § Shares and `ops share list|access|add|permission|remove|with`: a project, a deliverable, or a task to another org or one person, as `reader` or `editor`. Only an owner or an admin shares. No undo.
- **Holds.** `knw-ops-data_model` § Holds and `ops task holds <task>`: a lease of an actor (`take` or `chair`, 600 s by default) on a task or a project. The CLI only reads holds.
- **Calendars and events.** `knw-ops-data_model` § Calendars and Events, `ops calendar list|show|create|update|delete|default`, and `ops event list|show|create|update|delete|attach|detach|for`: timed events, all-day events, periods (an all-day event of more than one day: `--date <first> --until <last>`), repeats with `--occurrence <day> --scope this|following|all`, people, guests, and links to tasks and deadlines. The default calendar is a choice of each person.
- **The deliverable move** (Task 408). `ops deliverable move <deliverable> --to <project>` (`deliverables.move`): the sections and the tasks go with it, and the name moves into the new project.
- **Named sections** (Task 406). Each project, deliverable, and deployment has one locked section with its name (roles `backlog`, `main`, `inbox`). A deliverable gets its main section at its create, and a task with only `--deliverable` lands there (not in the first open section). The code `section_named_locked`.
- **Subtasks have one level** (Task 409). A subtask has no subtasks, and a task with subtasks cannot become a subtask (`subtask_too_deep`). `ops task subtask indent` is gone; `ops task subtask children <task>` is new (`subtasks.children`).
- **Sections have no priority** (Task 413). `ops section priority`, `subsections.setPriority`, and the field `priorityColor` are gone. The priority of a task stays.
- **The data mode** (Task 415). A dev build of `ops` uses PROD data by default, with the sign-in of `nuu login`. `OPS_DATA_MODE=dev` gives dev data. The order is `OPS_DATA_MODE`, a test run, `NUU_DATA_MODE`, `~/.nuucognition/dev-data.json`, then prod. The file `~/.nuucognition/ops-dev-data.json` is not read any more. The init, `knw-ops-cli`, `sk-ops-use_operations`, and the headless callouts of the four workflows say it.
- **Other commands.** `ops notify read-prefix <prefix>` and `ops notify dismiss-all`, `ops comment people` and `ops comment count`, `ops address rename <record> <name>|--clear`, `ops notepad block|section|make-task|undo-make-task` (`ops notepad scope` is a hidden alias of `ops notepad section`), and `ops favourite reorder <records...>`.
- **No fallback to the former ops.** The CLI 0.1.0-dev.3 needs a deployment with the current ops: the fallbacks to the ops of before the revamp are gone (`tasks.place`, a close through `tasks.update`, `subsections.*`, the old project snapshot, the former backlog view). The read of the headers keeps its fallback. The hidden `ops folder`, `ops deployment end-chain|reopen-chain`, and `ops section deployment` are gone. The init and `knw-ops-cli` say it.
- **Day labels are gone** (Task 390): a day label is an all-day event now. `ops day-label`, the ops `dayLabels.*`, and the kind `day-label` of `agent.resolve` leave the init, `knw-ops-cli`, `knw-ops-data_model`, and `sk-ops-use_operations`.
- **Review round 1 of the fleet.** `knw-ops-cli` names the `ops step` verbs that take a stream step (all but `add` and `move`: use `ops stream step add` and `ops step place`), gives `cross set` and `cross add|remove`, and `workspace streams set` and `streams add|remove` their own syntax, and lists the real options of `ops event update` (no `--attach`: use `ops event attach`). `knw-ops-data_model` loses the row `subsections.setPriority` and the colour of a moved section. `--deliverable` puts a task in the main section. The troubleshooting row of the wrong data gives `OPS_DATA_MODE=dev` with the dev launcher.
- **The main skill.** `sk-ops-use_operations` gets the new entities in the model table, the new jobs, five new recipes (a Trident lane, a deliverable move, a share, a period on a calendar, and a review request), the new codes in Troubleshooting, and the new safety rule on shares and moves. The init gets the model, the job table, and the headless rule 10.

# 0.5.0

- NUU Ops removed the task outcome (operator page feedback, 2026-11-04): a done task is done, with an optional result. No `completed`, `dropped`, or `superseded`. `ops task close` loses `--outcome` and takes only `--result`; `ops task done` sends no outcome; `ops task show` shows no outcome. Split, merge, and continue close the open old task. `tasks.close` still takes `outcome` and ignores it, so an older CLI still works. The model (`knw-ops-data_model` § The Task Primitive), the CLI knowledge, `sk-ops-use_operations`, `sk-ops-read_task_map`, and the init lose the outcome.
- Looped In (amendment 1 of Task 402 of the NUU Operations Flint): the people looped into a task follow it beside its owner, and each one hears every comment. A review request loops in the reviewer, and a mention in a comment loops in the mentioned member. The model (`knw-ops-data_model` § Looped In: the field `tasks.loopedIn`, the ops `taskLoops.add|remove`, the rules, and the code `loop_full`), the CLI knowledge (`ops task loop add|remove <task> <person>`, and the `looped in` line and `loopedIn` of `ops task show`), and `sk-ops-use_operations` give it.
- **Your Reviews** lists the open requests that you asked of other people ("You asked for"). `reviews.mine` gives them as `sent`, and `ops review list` shows them in the section `you asked for`.
